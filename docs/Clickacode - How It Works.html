Architecture notes

Clickacode Under the Hood

Clickacode is a fork of VS Code. Open a Python file and it runs the file, captures the value produced by every statement, and draws an interactive picture of each value at the end of the line that produced it. Type a character and the pictures update a tenth of a second later. Drag across a string in one of those pictures and a line of Python appears below, extracting what you selected. Keep dragging and that line rewrites itself in place.

This page explains how that is put together, for someone asking "how did they implement that?" rather than someone about to edit the code. It stays at the level of processes, protocols, and the ideas that hold the design together. The widgets shown here are HTML recreations of the real ones, not screenshots.

Three processes

Clickacode is spread over three running programs. Two are ordinary VS Code processes with new code added; one is Python.

The choice that shapes everything else: every run is a fresh Python process that executes the whole program from the top and then exits. Nothing survives between keystrokes except what the renderer chooses to send back in with the next run. That makes the system easy to reason about, and most of the engineering below goes into making it fast anyway.

Anatomy of one run

When the renderer decides the program should run, about 100 ms after the last keystroke, the following happens.

The rewrite step deserves a word. The runner parses the source into an abstract syntax tree, walks it, and inserts a logging call after each interesting statement. The rewritten tree is compiled directly, and because tree nodes keep their original line numbers, tracebacks and line attribution stay correct. There is no sys.settrace, no debugger, and no string-level code generation.

What gets logged, and how a widget knows who it is

Statements that produce widgets

The rewriter treats each statement kind a little differently, but the pattern is always the same: evaluate the expression once into a temporary, do what the original statement did with the temporary, then log the temporary. Evaluating once matters because expressions can have side effects.

StatementWhat is logged
x = exprthe value, tagged with the name x
x += exprthe result after the update
if test:the test's truth value
for a, b in ...:each loop variable, at the top of each iteration
return exprthe returned value
bare expressionits value
print(a, b)each argument separately, as well as the text going to the console
def f(x, y):each parameter, at the top of each call

Not logged: while tests, annotated assignments, with targets, comprehension internals, lambdas.

Along with the value, each log site carries the name and source text of what produced it, and sometimes the exact source span of the expression. The span is handed out only where the value literally is an expression written on the line, because that is the only case where a visualizer may legitimately rewrite it in place. The table's Sort does exactly that.

Identity: line and site

A line can have more than one log site (for a, b in ... has two). Each site gets a static index at rewrite time, and a widget's identity is the pair of line number and site index. It is stable across runs and across loop iterations, and it is the key everything else hangs off: the visualizer's saved state, the queue of pending UI events, the on-screen DOM node.

When the user edits the file, the renderer shifts these line numbers itself using the edit's line delta rather than waiting for a run to say where things went. A command that arrives from Python after the user inserted a line above is translated through a small map from "the line Python was told about" to "where that line is now."

Paths: which iteration, which call

A line inside a loop runs many times, so "the value of this line" really means "the value in some iteration." The rewriter wraps every loop and every function body in enter and exit hooks, and the runner keeps a stack of header-line and iteration-number frames. Every logged item carries a copy of that stack, its path. A function is treated as a loop over its calls, so a slider on a def line picks a call the way a slider on a for line picks an iteration. Recursive activations are numbered in entry order.

When a loop or function finishes, the runner sends a loop message with the header line and the count. That is what sizes the slider on the header line.

The execution step

The runner also increments a counter on every log call, whether or not the value is rendered, and each item carries its value. It is the total order over "moments in the program" that the checkpoint 3 optimization below depends on.

Visualizers: Elm in Python

A visualizer is a Python module whose filename ends in _visualizer.py. The runner loads them from three places in priority order: a .snc_visualizers/ folder in the workspace, one in the home directory, and the built-in set that ships with the app. Within a folder they are tried alphabetically and the first whose can_visualize(value) returns true wins. That is why the fallback object visualizer's filename starts with z_, and why the error visualizer sorts first.

An interactive visualizer follows the Elm architecture, implemented by hand in Python:

  • init_model(value, …) returns a JSON-serializable dict of UI state.
  • visualize(value, model, …) returns HTML.
  • update(event, model, value, …) takes one UI event and returns a new model plus a list of commands for the editor to carry out.

A static visualizer only needs can_visualize and visualize. Visualizers ask for optional extras simply by naming them in their signature; the runner inspects each function once and passes only what it asks for. That is how an older or third-party visualizer keeps working as the runner learns to offer more.

The value is never stored in the model. The model holds only UI state, and the value is passed fresh every run. This is what lets a model survive an edit that changes the value.

The built-in set

  • Strings are drawn one character per element, with visible markers for start and end of string and for newlines. This is the visualizer that builds regular expressions by demonstration.
  • Lists and dicts become a table with configurable columns, each column a Python expression over the row. Per-column menus filter, sort, convert types, group, and aggregate. The table paginates at 50 rows while always showing the last three, because a list is as much its end as its beginning.
  • Tuples and named tuples are a row of child visualizers. The tuple visualizer deliberately has no search or actions: a tuple is a collection of unlike things. What it contributes is a name for each element, so every element is a drag handle.
  • Everything else goes to an object visualizer showing accessor → value rows, with autocomplete for adding fields.
  • NumPy and pandas values get read-only summaries. These modules recognize their types by module name rather than importing the libraries, so a run without NumPy never pays NumPy's import cost.
  • An uncaught exception is wrapped in a marker type and rendered in red at the line that raised it, in the iteration that raised it. The wrapper exists so an exception the program caught and is merely holding still renders as an ordinary object.

Nesting

A table cell holding a string gets the string visualizer; a tuple element holding a list gets the table. A parent asks the runner for the right child visualizer, wraps the child's HTML in an element tagged with a child key, and the renderer wraps any event from inside that element as a child event so the parent can route it down. Only the child that currently has focus receives events; the first click on an unfocused child just moves focus, so sweeping the mouse across a table cannot hijack it. Nesting depth is capped as a cycle backstop.

Focus and the small rendering

The renderer tells Python which line the cursor is on. Every widget on any other line renders in a compact form with no toolbars or search boxes. Clicking a small widget pins focus to it and reruns immediately. This is why a file full of widgets does not turn into a wall of toolbars, and also why moving the cursor is itself a reason to rerun.

Visualizers can evaluate in the program's scope

At each log site the rewriter also injects a tiny lambda that calls eval at that point in the program, and visualizers receive it. A table column written as $ * factor can therefore refer to the program's own factor variable. There is no sandbox here; this is eval inside the user's own process. The mitigations are conventions: catch exceptions, and never touch the user's random state, since visualizer code runs between the user's statements and would otherwise shift every subsequent random draw.

Determinism and hot reload

Because the program runs dozens of times a minute, nondeterminism would make the pictures flicker. The runner seeds random and numpy.random after the imports, and workers start with a fixed hash seed so set iteration order is stable. A user's own random.seed() still wins.

At the start of every run the runner compares each visualizer file's modification time against the one it loaded and re-executes changed modules. The runner itself cannot reload, so the main process checks the runner's modification time before each run and drains its worker pools if it changed.

The interaction round trip

This is what makes the system feel like an application rather than a debugger display.

HTML attributes carry Python

The HTML a visualizer emits has attributes like snc-mouse-down="MouseDown(index=17)". The value is Python source: the repr of a small dataclass constructor defined in the visualizer's own module. The renderer never interprets these strings. When a DOM event fires it walks up from the target to the nearest element with the attribute and sends the string back with a deliberately minimal event record: type, buttons, modifier keys, and the typed value for input events. No coordinates cross the wire, so two identical mouse moves are byte-identical and can be deduplicated. Python's update evaluates the string in the visualizer module's namespace and gets the event object.

There are shorthands. An element tagged snc-idx="5" expands to mouse down, move, and up events at index 5. For runs of text the renderer uses the browser's caret-from-point API to resolve the exact character under the pointer, including the gaps between spans and the space past the end of a line.

Events queue on their widget and travel with the next run

There is no persistent Python process to send an event to. So the renderer stamps each event with an id, appends it to its widget's queue, and starts a run. The run carries every widget's model and queue. When the runner's logging call reaches a widget it applies the queued events through update, renders, and reports on the resulting item which event ids it handled. The renderer requeues anything unhandled, retries exactly once, then drops it rather than spinning runs forever. Events for a widget a completed run never reached are dropped too.

Why report handled ids rather than assume everything sent was applied? Because the runner declines to replay events onto a model it had to rebuild. A model is reused only if the value's type fingerprint, the source expression, and the line's saved configuration all match; otherwise init_model runs fresh, and replaying old events onto it would be wrong.

An event does not always need its own run

A run reaches a given widget long before the program ends. If a run is in flight and has not yet emitted the item for the widget the event is for, the renderer hands the event to that run: the main process writes an events message onto the worker's stdin, and the runner drains its stdin just before it looks up a widget's pending events. No new run starts.

One consequence on the Python side: exactly one reader owns the protocol file descriptor with its own byte buffer, and sys.stdin.readline() is never used alongside it. A buffered text reader would read ahead and silently swallow an events message arriving hard behind a run message.

Commands ride on the item

When update returns commands (insert this code, copy this text, rewrite this comment), they are attached to the same item message as the rendered HTML rather than sent separately. A run can be killed at any instant by the next keystroke. If the command were its own message, a run could die between the item that retired an event and the command that event produced, and a drag's line of code would silently never be written. One message means both or neither.

What the renderer does with the HTML

Each item becomes an overlay widget positioned in absolute pixels at the end of its line. Overlay widgets float, so each line also gets an empty view zone under it to reserve vertical space. A widget that grows past 150 px in either dimension switches to a block layout under the line, aligned with the code's indentation.

Widget content is replaced by a full innerHTML swap, but the renderer saves and restores focus (by element name), input selection ranges, any text typed since the render was requested, and the scroll position of every scrollable descendant, so a rerun mid-drag is invisible. Byte-identical HTML is skipped entirely, and view zone heights are only replaced when they actually changed, because changing one relays out every line below it.

Keeping the editor from jumping is its own subsystem. Before changing zones the controller anchors on the focused line, or the line nearest the viewport's midpoint, and restores the scroll offset afterwards. When content above the viewport shrinks and the needed scroll would be negative, it inserts a phantom spacer at the top of the document and melts it away as the user scrolls down.

While the file has a syntax error, widgets are greyed out and made non-interactive rather than removed, so the last good picture stays on screen while you finish typing.

A fresh process per keystroke, made fast

A Python process takes a noticeable fraction of a second to start, and import pandas alone can take a second or more. Three tiers of pre-warmed workers hide this, each five workers deep.

Checkpoint 1 workers have started Python and loaded the runner and all visualizers. A keystroke takes one and a replacement is spawned.

Checkpoint 2 workers have also executed the program's leading import statements. Editing the body of a program does not change its imports, so almost every keystroke can use one. The main process keys these workers by a cheap line-scan of the leading imports; the worker re-checks with a real parse and, if the imports turn out to differ, executes them itself. A wrong guess only costs speed, never correctness.

Checkpoint 3 workers have gone further: run up to the log site of the widget the user most recently interacted with and paused there. When a run arrives, the worker applies the event to that visualizer and runs only the tail. This is valid only while nothing that could change what the prefix does is different: the code, the file path, the cursor line (which changes every widget's small or full rendering), loop pins, the stdin document, live-only mode, and which widget to stop at. Any change kills the pool. Cursor movement therefore invalidates it, which is why checkpoint 2 gave up half its workers to fund it rather than the pool being bigger.

A paused worker has no run to attribute its output to, so it holds everything the prefix produced and releases it under the arriving run's id, except items, which it drops because the renderer already holds byte-identical ones from the run that warmed it. The renderer, told through a resumed message which execution step the run started from, keeps on-screen widgets whose step is earlier than that. If the prefix never reaches its target (an untaken branch, an exception above it), the worker discards itself rather than serve a run whose gesture would land on a program that already finished.

Several scheduling rules came out of real lag investigations:

  • A run waiting for a worker outranks warming one. A worker reaching checkpoint 1 while a keystroke has nothing to run on is handed over immediately instead of being sent off to import.
  • Queued runs are dropped, not served. A new run supersedes the one in flight, whose worker is killed, and every run still waiting for a worker. Under a flood of mouse moves the queue itself is the latency.
  • Pools refill as workers are taken, not when runs complete. A burst of runs never reaches end, since each kills the previous one, so refilling on completion would drain the pool and dump the burst onto cold workers.
  • A warm is bounded by a ten-second timer. A prefix with a sleep or a non-terminating loop would otherwise leave five workers spinning silently. On expiry further checkpoint 3 warms are suppressed until the key changes.

A run itself has a 60-second timeout, and every worker serves exactly one run and exits.

Two more speedups live elsewhere. Network reads are cached: the runner patches urlopen so a program that downloads a URL is served from a cache folder beside the file, keyed by URL hash. Entries last for the app session, and editing the line is how you force a refetch. And the renderer suppresses events aggressively: mouse moves are throttled to 16 ms, identical moves are dropped, moves over small widgets and idle moves over plain characters never leave the renderer, and an empty event string is treated as a no-op rather than costing a run.

Where state lives

Because Python is stateless between runs, everything that must persist is owned by the renderer or the file.

StateLives inTravels how
Visualizer UI state (model)renderer memory, keyed by line and sitesent with every run, returned on every item
Pending UI eventsrenderer memory, per widgetsent with every run; handled ids come back
Columns and fieldsa #%click comment in the source fileparsed by the runner; rewritten via a command

Last-touched widgetrenderer memorydrives checkpoint 3

The #%click comment deserves a word. What a visualizer wants to remember across sessions (a table's columns, an object's shown fields) is saved as JSON in a comment directly above the line that produced the value:

#%click [{"expr": "$['name']"}, {"expr": "$['orders']", "children": [{"expr": "$.total"}]}]
people = [{'name': 'Alice', 'orders': [...]}, ...]

The comment binds to the next non-blank, non-comment line, so inserting blank lines or ordinary comments does not re-bind it. The JSON is a list of slots, each an expression with optional children, and it has no type keys: a configuration written for one shape of value applies to whatever the line holds now, and an expression that no longer fits shows an error cell rather than being silently dropped. The editor folds each comment's JSON to a … chip and unfolds it only on click, since the JSON is storage, not something to read. A hash of the slots is stamped into the model, so a comment edited by hand or swapped in by a git checkout rebuilds the model, while the visualizer's own save does not.

From clicks to code

This is the part most specific to Clickacode. Several distinct ideas combine.

Commands

update can return commands the editor carries out:

  • NewCode: a suggested variable name, a line or block of code, the imports it needs, and optionally a #%click configuration the new line should open with, so a line generated from a table inherits the table's columns. The editor inserts the code after the triggering line at the right indentation (deeper if the trigger line opens a block) and picks a variable name that does not collide with anything in the file. Only the editor decides where a missing import re goes, because only it knows the file as it stands.
  • ChangeSelectedText: rewrite a range that a previous NewCode created. This is what makes continued dragging update the line in place rather than stacking new lines.
  • SetConfigComment: rewrite the line's #%click comment.
  • CopyToClipboard.

An undo stop is pushed on every widget mousedown, so each gesture's edits become their own undo step. After a NewCode the caret stays on the trigger line so the visualizer keeps focus and the user can keep interacting with it. The inserted line is then linked to the widget: a chain icon appears in the widget's corner, an arrow is drawn from the widget to the line, and further gestures rewrite that line. Clicking the chain unlinks; clicking again can re-link by parsing the existing line and adopting it rather than clobbering it.

A grammar that runs both ways

Each generating visualizer has a grammar: a set of named rules, where a rule is a template with typed holes such as "{var:Var} = {expr:Action}", a regular expression, or a validator like ast.parse. Every rule also carries a dictionary of context constraints: only when the search is case-insensitive, only when the action is replace.

The string grammar has roughly twenty actions (get a slice, first match or all matches, split, replace, delete, filter, count, any/all, loop over matches, find indices, and a family for when the input is itself a list of indices or index pairs), each with variants driven by context flags: case-insensitive picks re.I, first-only picks count=1 or next(..., None). The table grammar has the same shape over rows, with an extra axis for whether the value is a dict (a dict filter must write a dict comprehension, not silently yield keys) and whether the user's expression referred to the row index, which forces enumerate. The grammar also owns variable-name suggestion: data_filtered, str1_matches, parts, or nothing for statement-shaped actions like loops.

Strings by demonstration

Dragging across the top half of characters makes a literal segment; dragging across the bottom half makes a fuzzy one. For a fuzzy drag the visualizer enumerates candidate patterns and picks the most specific character class that matches exactly the dragged text without overshooting either edge, in a fixed order. The result is stored as an ordinary Python search string such as r'hello.*world', with optional postfix flags for first-only, case-insensitive, and capture. Segments can be resized by handles, split, deleted, or have their class or quantifier changed from a per-segment menu.

A pick tool decomposes the first match into chips: start, prefix, each group, suffix, end. Selecting chips assembles an expression with algebraic simplification, so prefix plus match plus suffix collapses to the whole string, and match plus suffix becomes a slice from the match start. In multi-match mode each chip becomes a comprehension over re.finditer.

When the string looks like a URL or names an existing file, a Fetch menu offers to generate the line that reads it as text, JSON, CSV, or Excel. Dragging a URL, or a tab from the integrated browser, into a Python file generates the same read.

Tables: the expression is the single source of truth

Table columns are Python expressions in a small dollar notation: $ is the cell, $$ the row, $$$ the whole list, and *$.members splats a sub-list into sub-columns. Per-column searches are written in the column's scope and then lifted and folded into one search string in the main search box, so the composition is visible and editable as text. An aggregation is its expression: the same string is stored, evaluated for the preview, and handed to the file on drag, so the number on screen and the code in the file cannot drift.

Some table actions do not generate a new line at all. Sort rewrites the very line the table is showing, using the source span from earlier: data = json.load(f) becomes data = sorted(json.load(f), key=lambda item: item['b']). The visualizer declares which part of the expression it considers incidental, so its own rewrite does not throw away the user's search configuration. Group By writes a walrus-based expression that yields a dict of lists, which the existing visualizers already know how to draw, so grouping needed no new drawing code.

Children generate code without knowing where they are

A nested visualizer never sees the parent's dollar expression. The parent binds the cell value to a fixed placeholder name, the child generates ordinary Python against that name, and the parent substitutes its own expression back in. Nested visualizers never link to a line; only the top-level one does.

Dragging expressions out

Many elements can be dragged into the code as text. An element can carry several expressions (a tally row is both "how many times this value occurs" and "which rows it occurs in"), each with the imports it needs. Drags carry a custom MIME type alongside plain text, and a drop provider on the Python editor inserts the text and the imports.

Loops and the slider

Every item carries its path, and a slider appears on the header line of any loop or function that ran at least twice. Moving the slider sends the pin, header line to iteration, with the next run. Selection happens in Python: the logging call drops any value whose path disagrees with a pin before choosing a visualizer, so only the pinned iteration is rendered or transmitted. Rendering at the moment of logging is also what makes this correct for values mutated across iterations; recording every iteration and scrubbing locally would need deep copies. A loop with no pin renders every iteration, each replacing the last on screen, so the last iteration is what stays.

Pins are keyed by a decoration on the header line rather than a line number, so edits above the loop do not re-key them. When a loop's reported count shrinks below a pin, the editor moves the pin and reruns. A site logged repeatedly in one run applies its pending events on the first logging and carries the resulting model through the rest, so a command emitted in response goes out once.

The console

A program that reads stdin cannot be handed a live pipe: the worker's real stdin is the command channel, and every rerun is a new process. So the console follows the same rule as visualizer state. The renderer owns the input and Python replays it.

The user's typed input is a document beside the source file, created only once a program actually asks for input. It is sent with every run, and a stand-in sys.stdin replays it so input(), sys.stdin.read(), and iteration behave identically every time. A read past the end of the document raises a special exception derived from BaseException, so a user's except Exception: cannot swallow it; that unwinds the run cleanly and reports "awaiting input." Statements after the read simply do not run, as in a terminal session that has not got there yet. End of stream is a literal <EOF> line, inserted with Ctrl-D.

The document opens as an ordinary editor tab, first in a group beside the source, narrowed to a third of the width. Being a real editor means find, undo, multi-cursor, and split all come for free. Output is committed atomically when a run ends unless the run exceeds 150 ms, after which it streams live.

Live-only mode

A setting, live-only visualizers, turns off code generation. Under it a visualizer is only a view: no drag handles, no action buttons, no chain icon, no drag-to-select, no column search, sort, or compute menus. Expanding, scrolling, picking an iteration, and adjusting table columns still work, since those change only the picture. It is enforced on both sides: visualizers omit the affordances, the runner filters outgoing commands down to copy and config-comment writes, and the renderer refuses code-writing commands and strips any expression attributes from HTML that still carries them.

A wrench badge in the editor's top corner is shown while visualizers can write code, next to an eye button that hides all widgets globally. The wrench is informational, not a control. The setting exists for the user study: the same tool, with and without code generation.

Study logging

Because the tool exists to be studied, it records how it is used. Every window appends JSON lines to one file per app launch in the user data directory; nothing is uploaded. Records cover session start (including a description of the git checkout, with a hash of the uncommitted diff so two sessions on identical work can be matched), editor and file lifecycle, periodic full-text snapshots of changed files, every run with its trigger and timing, every item, every widget event with a compact description of the DOM element hit, every command, and which edits were machine-written versus typed. Mouse moves are coalesced at 250 ms per distinct event string. The renderer buffers and flushes to the main process every second or every 500 events, and on shutdown, so a hard crash can lose about a second.

Known limits

  • There is no sandbox. Visualizer expressions are evaluated inside the user's process, and the user's program runs every 100 ms with whatever side effects it has. Network reads are cached, but file writes are not intercepted.
  • A paused checkpoint 3 worker holds the visualizer modules it loaded, so editing a visualizer file does not reach it until the Python file changes. Typing and deleting a space is the usual workaround.
  • The stdin document cannot contain the literal line <EOF>.
  • The cheap import scan in the main process can disagree with Python's parser on exotic input; this only costs a warm worker.
  • Widgets are laid out only for visible lines, which the editor already restricts, but there is no further virtualization of very large numbers of items.
  • Generator and async functions get no call frames, since a frame pushed on entry cannot follow a function that suspends.

Clickacode is a research prototype built on VS Code 1.130. Pool sizes, debounce timings, and other numbers here describe the code as of September 2026 and will drift. Widget images on this page are HTML recreations, not screenshots.
